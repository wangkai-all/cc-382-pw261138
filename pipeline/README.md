# 字段分类变更的精确阻断管道（pointwise-delivery）

字段分类从「普通」改为「敏感」后，依赖它的清洗表、聚合表和导出会被自动重新评估：
受影响产物被精确阻断，安全替代版经人工审批后放行，被阻断的数据通过可追踪标记
核对确实不再分发。

## 系统组成（三个独立服务 + 网页控制台）

| 组件 | 端口 | 职责 |
|---|---|---|
| `registry_service.py` 分类登记服务 | 7801 | 字段分类、表达式级血缘、影响分析、审批、审计；同时托管网页控制台 |
| `scheduler_service.py` 加工调度器 | 7802 | 执行真实加工管道（源表→清洗→聚合→导出），每次运行上报列级血缘 |
| `publisher_service.py` 发布服务 | 7803 | **发布时**按当前分类判定；复核/隔离已分发产物；标记扫描自检 |

服务间只通过 HTTP 协作，各自持有独立的 SQLite 库，可单独启停。

## 加工管道（真实执行，非模拟）

```
customers.csv ─┐
               ├─ clean_customers → stg_customers ─┬─ export_billing（直出 phone）
orders.csv ────┴─ clean_orders → stg_orders        ├─ export_marketing（含拼接列/UDF列）
                       │                           ├─ export_marketing_safe（安全替代版）
                       └─ agg_daily_sales（聚合）──┴─ export_partner_feed（k≥10 匿名化）
```

关键设计：**规则不只看最终列名**。调度器上报的是列级血缘 + 转换方式：

- `contact_blob = lower(email) || '|' || phone` —— 列名不含 phone，但拼接表达式保留来源
- `profile_note = udf_profile(phone, signup_date)` —— 外部 UDF，表达式不可解析 → `unknown`

## 传播规则（判断依据）

| 转换 | 判定 | 依据 |
|---|---|---|
| copy / concat / substring / lower / trim | 敏感性原样传播 | 来源数据原样或近似原样保留 |
| hash | 视为保留 | 手机号等低熵值可彩虹表逆推 |
| mask（留后4位） | 降级为「需审批」 | 假名化：仍可链接，外部发布需人工批准 |
| aggregate 且最小组 k≥10 | 匿名化，不再传播 | 组足够大，个体不可反推 |
| aggregate 且 k<10 | 按保留处理 | 小样本组可反推个体 |
| **unknown**（不可解析表达式） | **fail-safe 按敏感阻断** | 无法证明不含敏感来源，列入人工核查 |

每个导出物得到三级判定：`ok`（可发布）/ `needs_approval`（安全替代版，需审批）/
`blocked`（阻断）。判定响应中携带完整的传播路径作为**判断依据**，网页上逐级展示。

## 未知情况的处理

- 不可解析的表达式（外部 UDF）一律 fail-safe 按敏感阻断，并在判定结果中单独列为
  「未知项」，指向具体列与路径，等待人工核查血缘；
- 发布服务复核时遇到登记服务无法评估的产物，同样 fail-safe 隔离；
- 调度器记录作业运行起止时的分类版本，执行期间发生版本漂移会标注提醒。

## 旧加工任务晚完成

判定发生在**发布时**而非调度时：任务启动时读到的分类版本已无关紧要。
晚完成的产物（`started_at` 早于分类变更、现在才产出）在发布环节按**当前**分类
重新评估，阻断依据中会明确标注「晚完成」。网页上有按钮可直接模拟这一场景。

## 精确阻断 vs 全部停止

全部停止当然安全，但影响面最大。本系统基于表达式级血缘做精确阻断：
`customers.phone` 改敏感后，4 个导出中仅 2 个阻断、1 个转审批，
`export_partner_feed`（k≥10 聚合）全程不受影响。分类变更接口与网页都会展示
两种策略的对比。

## 安全替代版审批

`export_marketing_safe` 去除了拼接列与未知 UDF 列、手机号仅留掩码，判定为
`needs_approval`。审批绑定 **（导出名, 内容哈希）**：内容一旦变化需重新审批，
防止「审批一个版本、发布另一个版本」。

## 可追踪标记核对

虚构源数据中 12 个客户的手机号为 `CANARY-PHN-00xx`、邮箱为 `canaryxx@example.com`。
核对方式：扫描分发目录（`data/distribution/`）中的标记数 —— 被阻断后必须为 0；
被阻断的产物移入隔离区（`data/quarantine/`），标记留在那里属正常（受控、未外发）。
发布服务提供 `/scan` 自检接口，网页「审计与标记扫描」页实时展示。

## 运行

```bash
# 端到端核对（自动启动三个服务、跑完整场景、37 项断言）
python3 pipeline/verify.py

# 跑完保留服务，打开网页控制台继续操作
python3 pipeline/verify.py --keep
# 然后访问 http://127.0.0.1:7801/
```

网页控制台四个页签：① 字段分类（修改分类、立即看到受影响导出与两种策略对比）
② 影响路径（传播树 + 每条边的判断依据）③ 导出与发布（尝试发布 / 批准安全替代版 /
模拟旧任务晚完成 / 复核）④ 审计与标记扫描。

## 核对结果（verify.py，37/37 通过）

1. 基线：全部 normal 时 4 个导出均可发布，标记确实随数据流出（证明管道真实连通）
2. `customers.phone` 改敏感后：billing/marketing 被隔离，marketing_safe 转待审批，
   partner_feed 保留分发，分发目录标记清零
3. 重发 billing 被阻断，依据为 copy 直达路径
4. 晚完成的旧任务产物仍被阻断，依据中标注「晚完成」
5. 安全替代版未审批不可发布 → DPO 批准 → 发布，掩码值不含标记
6. 未知转换 profile_note fail-safe 阻断并列入核查；contact_blob 列名不含 phone
   仍被血缘判定敏感（证明列名规则会漏判）
7. 终检：分发目录标记数 = 0，隔离区存有被阻断的标记数据

## 限制（演示性质）

单机进程、CSV 文件存储、无鉴权；「分发」以分发目录模拟外部伙伴可取的存储桶，
「阻断不再分发」= 不再新增 + 已分发副本移入隔离区（现实中已外发数据无法收回，
这里建模的是可撤回的对象存储/取数目录场景）。真实落地时血缘需从 SQL 解析或
计算引擎（如 Spark/OpenLineage）采集，本演示中由作业定义显式声明。
